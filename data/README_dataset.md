# SupplyShield Synthetic Dataset

A realistic, synthetically generated pharmaceutical supply-chain dataset
matching the MongoDB collection schemas and Neo4j graph schema defined in
the SupplyShield proposal (Chapter 4). Generated by `generate_dataset.py`
with a fixed random seed (`42`) so it's fully reproducible.

## What's in here

```
dataset/
  reference/
    entities.json          135 supply-chain entities (manufacturers,
                            distributors, wholesalers, pharmacies)
  mongodb/
    batches.json            500 batch records
    shipments.json          2,598 shipment records
    inventory.json           2,591 inventory snapshot records
    transactions.json       2,599 ownership-transfer transactions
    recalls.json             10 recall records, with realistic
                            affected_entities derived from the actual
                            shipment graph
    users_seed.json         6 demo login accounts (PLAINTEXT passwords --
                            see "Loading into MongoDB" below)
  neo4j/
    entities.csv            same entities, as CSV
    batches.csv              501 rows (500 real + 1 planted duplicate --
                            see "Planted anomalies" below)
    shipments.csv            2,598 rows
    recalls.csv               recall -> batch mapping
    recall_affected.csv       recall -> notified-entity mapping
    load_graph.cypher        ready-to-run Neo4j bulk-load script

anomalies_manifest.json      exact IDs of 4 intentionally planted anomalies
generate_dataset.py          the generator (re-run to regenerate/rescale)
validate_anomalies.py        confirms the planted anomalies are actually
                            detectable by the same query logic used in
                            the proposal (Section 4.3 / Listing 4.8)
```

## Loading into MongoDB

Each `mongodb/*.json` file is a plain JSON array, ready for `mongoimport`:

```bash
mongoimport --uri "mongodb://localhost:27017/supplyshield" \
  --collection batches --jsonArray --file dataset/mongodb/batches.json

mongoimport --uri "mongodb://localhost:27017/supplyshield" \
  --collection shipments --jsonArray --file dataset/mongodb/shipments.json

mongoimport --uri "mongodb://localhost:27017/supplyshield" \
  --collection inventory --jsonArray --file dataset/mongodb/inventory.json

mongoimport --uri "mongodb://localhost:27017/supplyshield" \
  --collection transactions --jsonArray --file dataset/mongodb/transactions.json

mongoimport --uri "mongodb://localhost:27017/supplyshield" \
  --collection recalls --jsonArray --file dataset/mongodb/recalls.json
```

**`users_seed.json` is different** -- it contains plaintext demo passwords
(e.g. `Admin@123`) rather than bcrypt hashes, because hashing should happen
in application code, not in a static data file. Do **not** `mongoimport`
it directly. Once the backend's `scripts/seed.js` exists, it should read
this file, call `User.hashPassword()` (bcryptjs) on each password, and
insert the results into the `users` collection. Until then, treat this
file purely as a reference for demo credentials.

## Loading into Neo4j

1. Copy everything in `dataset/neo4j/*.csv` into Neo4j's `import/` directory
   (in the project's Docker Compose setup, this will be a mounted
   `./neo4j-import` folder -- see the backend README once it's built).
2. Run the load script:
   ```bash
   cypher-shell -a bolt://localhost:7687 -u neo4j -p supplyshield123 -f dataset/neo4j/load_graph.cypher
   ```
   or open Neo4j Browser and paste the contents of `load_graph.cypher` in.
3. This creates uniqueness constraints, then loads all four entity node
   types, `Batch` nodes with `PRODUCED` edges, `Shipment` nodes with
   `PART_OF` / `FROM` / `TO` edges, and `Recall` nodes with `AFFECTS` /
   `NOTIFIED` edges -- exactly the schema in Tables 4.1 and 4.2 of the
   proposal.

the recall/inventory statuses; see `SupplyShield_HANDOFF.md` sections 12 and 16.

## Planted anomalies (for demoing the counterfeit-detection engine)

Four specific, documented anomalies were deliberately inserted so you can
run the anomaly-detection queries from the proposal and show they actually
catch something real, rather than demoing against a clean dataset with
nothing to find. Exact IDs are in `anomalies_manifest.json`:

1. **`multi_manufacturer_batch`** -- one batch ID has two different
   manufacturers both claiming to have produced it (a duplicated/cloned
   batch identifier -- classic counterfeit signature).
2. **`duplicate_batch_fanin`** -- the same batch is shipped into the same
   wholesaler from two different distributors only 3 hours apart
   (matches Listing 4.8 in the proposal exactly).
3. **`abnormal_fanout`** -- one distributor ships the same batch to 18
   distinct wholesalers within 17 hours (2026-07-07 18:04 to 2026-07-08
   11:04 UTC -- it crosses midnight, so a calendar-day count sees 6 + 12),
   versus a network average of ~1.1 distinct receivers/sender/day.
4. **`reentrant_distribution`** -- one pharmacy receives the same batch
   twice, from two different wholesalers, a day apart.

**Side effect:** the planted shipments in (2)-(4) come from senders that
never received the batch -- stock with no provenance. That is 22 shipments,
all inside the three planted batches, and it is detected by a fifth rule,
`provenance_gap`.

**Organic repeat receipts:** 10 other (batch, receiver) pairs receive the
same batch twice from different senders (generator artefacts that look like
normal restocking, with full provenance). A naive "received twice" rule
flags 12 pairs; the narrowed rule (repeat receipt + provenance gap, not
already a fan-in) flags only the planted one.

`validate_anomalies.py` re-implements the detector logic directly over the
CSV data (without needing a live Neo4j instance). It expects 9 findings,
all inside planted batches, and exits non-zero otherwise -- run it with
`python3 validate_anomalies.py`.

Note on the fan-out check specifically: it must use a **rolling**
time window (24 h), not a lifetime cumulative count (most distributors'
cumulative counts converge over 18 months) and not calendar days (the
planted burst crosses midnight).

## Regenerating / rescaling

Edit the constants at the top of `generate_dataset.py`
(`N_MANUFACTURERS`, `N_BATCHES`, etc.) and re-run:

```bash
python3 generate_dataset.py
```

The random seed is fixed (`SEED = 42`), so the same constants always
produce the same dataset -- change `SEED` if you want a different draw
at the same scale.
